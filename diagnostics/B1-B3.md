# Why B1, B2 and B3 produced two reports per trigger in `browser-dev`

**Conclusion: (b), the development build of React behaving differently from the
production build.** In a React 18.3.1 **development** build, a render error that
an error boundary catches is *also* dispatched to the page as window `error`
events. That is two events per error in this app, and it happens on a page
with no SDK at all. The SDK reports a window `error` event the same way it
reports any uncaught error, so one trigger produces two reports:

1. an **uncaught-error report**, from the window `error` events;
2. the **`captureError` report** that the fixture's boundary sends, as DESIGN.md
   prescribes for B1–B3.

A production build of React, minified or not, dispatches **no** window `error`
event for a boundary-caught error, so only report 2 exists. That is why B1–B3
succeeded in `browser-prod`.

It is not (c), the SDK reporting the same error twice. Each of the two reports
corresponds to a distinct input the page gave the SDK: window `error` events,
and an explicit `captureError` call. Remove the `captureError` call and one
report remains. Remove the window events by using a production build and one
report remains. The SDK sent one report for the two or three identical window
`error` events of one render error, not one per event. Nor is it (a) in the
sense of a fixture defect: the second report is the boundary's `captureError`
call, which is the mechanism the design specifies for B1–B3. The fixture asks
for exactly one report, and the development build of React adds a second
input.

Everything here is observed input → output. Nothing assumes how React or the
SDK is built.

## 1. What the two captured reports are

These are from the frozen `browser-dev` capture log (B1, v1, attempt 1).
Across all 72 B1–B3 `browser-dev` attempts, the two POSTs arrive 0–30 ms
apart, and the order is always the same: first the uncaught-shape report
(with `description`), then the captureError-shape report (without it).

| Field | Report 1 | Report 2 |
|---|---|---|
| keys | `title, errorLog, description, severity, priority, project, breadcrumbs, browserInfo` | `title, errorLog, severity, priority, project, breadcrumbs, browserInfo`, with **no `description`** |
| `title` | `Uncaught TypeError: Cannot read properties of undefined (reading 'map')` (Chromium); `TypeError: can't access property "map", product.reviews is undefined` (Firefox); `TypeError: undefined is not an object (evaluating 'product.reviews.map')` (WebKit) | the React component stack (`\n    at ProductReviews (…/ProductReviews.jsx:4:34)\n    at ErrorBoundary …`), i.e. the second argument of `captureError` |
| `description` | `Auto-captured crash on /products/reviews` | absent |
| `errorLog` | the error's stack, whose frames include `HTMLUnknownElement.callCallback`, `Object.invokeGuardedCallbackDev`, `invokeGuardedCallback`, `beginWork$1` | the error's stack, a **different** stack of the same length, whose frames include `beginWork$1`, `performUnitOfWork`, `workLoopSync`, `renderRootSync`, `recoverFromConcurrentError`, `performSyncWorkOnRoot` |
| breadcrumbs | `navigation > click > error` | `navigation > click > error > error > console` (two `error` crumbs reading `Crash: Uncaught TypeError: …`, then React's console message `The above error occurred in the <ProductReviews> component…`) |

Report 1 has exactly the shape of every other uncaught-error report in the
corpus (`title` starting `Uncaught`, and a `description`). Report 2 has exactly
the shape of the `captureError` reports that B1–B3 produced in `browser-prod`.
The two `errorLog`s differ below the fourth frame, so the two reports carry two
different stacks of the same render error. Report 2's breadcrumbs record two
window errors before it.

## 2. Controlled experiment

The controlled app has one component with B1's defect (`product.reviews.map`
on a product without `reviews`), rendered after a click. It was built and
served four ways:

| Build | React build | Minified |
|---|---|---|
| `devserver` | development (Vite dev server, like `browser-dev`) | no |
| `devbuild` | development, bundled (`NODE_ENV=development vite build`, `minify: false`) | no |
| `prod-unmin` | production, bundled (`minify: false`) | no |
| `prod-min` | production, bundled (like `browser-prod`) | yes |

The bundles were checked. The two development bundles contain React's
development-only code; the production bundles contain the "Minified React
error" production code and none of the development-only code.

Each build was run with: boundary and `captureError` (the fixture's shape);
boundary without the `captureError` call; and no boundary. Each of those ran
with the SDK tag and without it, in a fresh context, in Chromium 156, Firefox
157 and WebKit 27.2: 72 runs in all. "Window error events" were counted by a
listener that an init script registers before any page script.

**The results were identical in all three engines:**

| Build | Configuration | Window `error` events (with or without the SDK) | `componentDidCatch` calls | Reports with the SDK | Report shapes |
|---|---|---|---|---|---|
| devserver | boundary + `captureError` | 2 | 1 | **2** | uncaught + captureError |
| devserver | boundary, no `captureError` | 2 | 1 | **1** | uncaught |
| devserver | no boundary | 3 | 0 | 1 | uncaught |
| devbuild | boundary + `captureError` | 2 | 1 | **2** | uncaught + captureError |
| devbuild | boundary, no `captureError` | 2 | 1 | **1** | uncaught |
| devbuild | no boundary | 3 | 0 | 1 | uncaught |
| prod-unmin | boundary + `captureError` | **0** | 1 | **1** | captureError |
| prod-unmin | boundary, no `captureError` | 0 | 1 | **0** | — |
| prod-unmin | no boundary | 1 | 0 | 1 | uncaught |
| prod-min | boundary + `captureError` | **0** | 1 | **1** | captureError |
| prod-min | boundary, no `captureError` | 0 | 1 | **0** | — |
| prod-min | no boundary | 1 | 0 | 1 | uncaught |

Without the SDK tag, the window-event counts are the same and no reports are
sent. The window events in the development builds all carry the same message
(`Uncaught TypeError: Cannot read properties of undefined (reading 'map')` in
Chromium).

What the table shows, as input → output:

- **Development vs production React decides whether a caught error reaches the
  window.** With a boundary, the development builds dispatch 2 window `error`
  events and the production builds dispatch 0. This holds without the SDK and
  without minification, so it is a property of the React build, not of
  minification and not of the SDK.
- **Each input produces one report.** Two or three window `error` events from
  one render error produce **one** uncaught-shape report. One `captureError`
  call produces **one** captureError-shape report. The dev builds give two
  inputs, so two reports. The production builds give one input, so one report.
- **The fixture's own requirement is one report.** Without the window events
  (production), boundary + `captureError` gives exactly one report, which is
  what DESIGN.md asks for.

## What this means for the corpus

The cause is not the fixture or the harness. The fixture does what the design
specifies, and the second report comes from the development React build.
**B1–B3 therefore stay dropped in all six `browser-dev` cells**, as the one-trigger,
one-report rule requires. They are measured in `browser-prod` only.

For the results document: in a development build, a React app using this SDK
with an error boundary that calls `captureError` sends two reports for every
render error, of two different shapes (one uncaught, one manual). Whether the
two are grouped together is a real grouping question, but this corpus cannot
pose it, because its ground truth is one report per trigger.
