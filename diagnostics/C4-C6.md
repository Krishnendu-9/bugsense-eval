# Why C4, C5 and C6 produced no reports in Chromium

**Conclusion.** The cause is neither the fixture nor the harness. It is not the
SDK's repeat suppression or per-session cap either. The reports genuinely do
not exist.

- **C4 and C5** (an unhandled `fetch()` that fails at the network level): this is
  observable **SDK-plus-engine behaviour**. When the SDK's `<script>` tag is on
  the page, Chromium dispatches no `unhandledrejection` event at all for the
  rejection, and no report is sent. Without the SDK tag, the same rejection
  does dispatch the event. The same effect was reproduced with no SDK at all,
  using a fetch wrapper of our own loaded from a no-CORS cross-origin script.
- **C6** (`res.json()` on an HTML page) is **engine behaviour**. Chromium
  dispatches no `unhandledrejection` event for that rejection even on a page
  with no SDK and no cross-origin script.

Firefox 157 and WebKit 27.2 report all three on the first attempt in every
cell. Chromium is 156.0.8078.4, the Playwright 1.64.1 headless shell.

Everything below is observed input → output. Nothing here relies on, or
guesses at, the SDK's internals. The SDK was loaded only through the
prescribed `<script>` tag, and its source was never fetched or read.

## Step 1: what every attempt actually did

The original capture logged, for each attempt, every request the capture
server received. All 48 Chromium attempts for C4–C6, across both environments
and versions, have `requests: []`. No POST arrived, no CORS preflight
(`OPTIONS`) arrived, and there was no harness failure. Playwright's
`pageerror` saw the intended error each time (`Failed to fetch`, or `Unexpected
token '<'…`).

In the original capture, retries were immediate, each in a fresh browser
context. The re-run therefore repeated every cell with the instrumented
harness:

- every attempt in a fresh browser context, each with its own `pageSessionId`
  (72 distinct ids for 72 attempts);
- each retry started at least 11 s after the previous attempt of the same
  trigger had **ended**. The measured minimum was 11,000 ms end to start, and
  about 21,800 ms start to start;
- each attempt records `postsReceived`, `requestsReceived` and an `outcome`
  from `ok`, `zero_reports`, `multiple_reports`, `report_before_click`,
  `trigger_failed` or `harness_error`;
- a "trigger raised" check based on what the page itself did. For C4 and C5,
  that is a `requestfailed` on the target URL; for C6, a `500 text/html`
  response from `/api/orders/history`. The page's own `error` and
  `unhandledrejection` events are recorded too, by listeners that an init
  script registers before any page script runs (and so before the SDK).

**Result (72 attempts):**

| Browser | Cells | Attempts | Outcomes |
|---|---|---|---|
| Chromium | 4 (2 environments × 2 versions) × 3 incidents | 48 | `zero_reports` × 48: trigger raised every time, `postsReceived 0`, `requestsReceived 0` |
| Firefox | 12 | 12 | `ok` × 12 (first attempt; 1 POST plus its preflight) |
| WebKit | 12 | 12 | `ok` × 12 |

In every Chromium attempt, the page evidence is the intended failure
(`requestfailed net::ERR_CONNECTION_REFUSED` for C4/C5; `response 500
text/html` for C6), plus a Playwright `pageerror`. **No `unhandledrejection` event
reached the page's own listener.** The full table is in
`diagnostics/rerun/C4-C6-attempts.md`.

## Hypothesis 1: a fixture race. Ruled out.

Endpoint reachability was probed from the harness immediately before each
click and again right after the page's failure had been observed (the
`requestfailed` or `response` event):

- **C4 and C5:** `127.0.0.1:7199` / `7198` and `[::1]:7199` / `7198` answered
  `ECONNREFUSED` before and after, in all 48 C4/C5 attempts (32 in Chromium, 16 in Firefox and WebKit). Nothing listened
  on those ports, and nothing was started or stopped around the trigger. The
  page saw `net::ERR_CONNECTION_REFUSED` for the target URL each time.
- **C6:** the mock backend answered `500 text/html` (`<!DOCTYPE html>…`)
  directly on `:7103` and through the app origin's `/api` proxy, before and
  after, in all 24 C6 attempts (16 in Chromium). The `eval-mock` container was
  `Up 4 hours` each time, so it was not restarted.
- **Capture server:** the harness posted a marker to it from Node before and
  after every attempt. A separate fresh browser context also fetched a marker
  after every attempt. All 216 markers (72 attempts × 3) were recorded, so the capture server
  was up and reachable from the browser throughout.
- The same fixture code in the same cells reported normally in Firefox and
  WebKit.

## Hypothesis 2: the SDK's repeat suppression or per-session cap. Ruled out.

- Every attempt ran in a new browser context. Retries started at least 11 s
  after the previous attempt ended, so neither a 10-second repeat window nor
  a per-session count can carry over between attempts.
- The **first** attempt in each cell was already `zero_reports`. Nothing had
  been reported in that context beforehand.
- Not even a CORS preflight was sent. A suppressed repeat would need an
  earlier report of the same error, and there was none.
- Diagnostic page (d) shows the SDK reporting normally in the same page,
  right after a fetch failure. A fetch rejection was caught and swallowed,
  then an unrelated `throw new Error('after')`, and that produced exactly 1
  report in Chromium.

## Hypothesis 3: what the SDK and the engine do. Characterised.

### Diagnostic pages (a)–(h)

Each case ran in a fresh context, once with the SDK tag and once without.
"Event" means the page's own listener, registered before any page script, saw
an `unhandledrejection` (or, for f and d, an `error`) event. Reports were
counted at the capture server. Pages without the SDK tag never send reports,
so their row shows only whether the event fired.

| Case | Input | Chromium, SDK tag: event / reports | Chromium, no SDK: event | Firefox, SDK tag: event / reports | WebKit, SDK tag: event / reports |
|---|---|---|---|---|---|
| a | `Promise.reject(new TypeError('Failed to fetch'))` from page code | yes / **1** | yes | yes / 1 | yes / 1 |
| b | real `fetch()` to a closed port, rejection unhandled | **no / 0** | **yes** | yes / 1 | yes / 1 |
| c | same fetch, caught, `BugSense.captureError(e)` | (handled) / **1** | (handled) | (handled) / 1 | (handled) / 1 |
| d | fetch rejection caught and swallowed, then `throw new Error('after')` | `error` / **1** | `error` | `error` / 1 | `error` / 1 |
| e | `TypeError('Failed to fetch')` with `stack` set to only its first line, rejected unhandled | yes / **1** | yes | yes / 1 | yes / 1 |
| f | the same hand-made error, thrown synchronously | `error` / **1** | `error` | `error` / 1 | `error` / 1 |
| g | `res.json()` on an HTML 500 page (same origin), rejection unhandled (the C6 shape) | **no / 0** | **no** | yes / 1 | yes / 1 |
| h | real `fetch()` to a closed port, awaited inside an `async` function, rejection unhandled (the C4 shape) | **no / 0** | **yes** | yes / 1 | yes / 1 |

The errors' `stack`, exactly as the page saw it. For b, g and h this comes
from an "observe" run in which the error was caught.

| Case | Chromium, SDK tag | Firefox, SDK tag | WebKit, SDK tag |
|---|---|---|---|
| a | `TypeError: Failed to fetch\n    at HTMLButtonElement.<anonymous> (http://localhost:7160/case/a?…:7:15)` | `@http://localhost:7160/case/a?…:7:15\nEventListener.handleEvent*@…:6:31\n` | `@http://localhost:7160/case/a:7:28` |
| b | `TypeError: Failed to fetch\n    at window.fetch (http://localhost:8090/sdk/bugsense.js:185:28)\n    at HTMLButtonElement.<anonymous> (http://localhost:7160/case/b?…:6:70)` | `""` (empty) | not a string (`name: TypeError`, `message: Load failed`) |
| c | same shape as b (top frame `window.fetch (http://localhost:8090/sdk/bugsense.js:185:28)`) | `""` | not a string |
| e, f | `TypeError: Failed to fetch` | `TypeError: Failed to fetch` | `TypeError: Failed to fetch` |
| g | `SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON` (no frames) | `""` | `""` |
| h | `TypeError: Failed to fetch\n    at window.fetch (http://localhost:8090/sdk/bugsense.js:185:28)\n    at http://localhost:7160/case/h?…:6:97\n    at HTMLButtonElement.<anonymous> (…:6:248)` | `""` | not a string |

On a page without the SDK tag, Chromium's stack for the same fetch failure
has the page's own frame at the top (`at HTMLButtonElement.<anonymous>
(…/case/b…)`), and the event fires.

What this shows, as input → output:

- In Chromium, an unhandled **real fetch failure** gets no
  `unhandledrejection` event, and no report, when the SDK tag is on the page.
  It gets the event when the tag is absent (b, h). With the tag present, the
  error's top stack frame as the page sees it is in
  `http://localhost:8090/sdk/bugsense.js`. That script is cross-origin to the
  page and is loaded, as the design prescribes, without a `crossorigin`
  attribute.
- The `stack` text is not what matters. An error whose stack is just
  `TypeError: Failed to fetch` is reported (e, f), and so is an error with the
  same message created by page code (a).
- The SDK does report these errors when it is handed them. The real fetch
  error passed to `BugSense.captureError` produced one report (c).
- `res.json()` on HTML gets no `unhandledrejection` event in Chromium with or
  without the SDK (g).
- Firefox and WebKit dispatch the event, and the SDK reports, in every case.

### SDK-free reproduction (i)–(m)

To check the engine rule on its own, these pages have **no BugSense SDK**.
Instead they load `wrap.js` from a second origin (`localhost:7161`). It is our
own script, which replaces `window.fetch` with `function (u, o) { return
origFetch(u, o); }` and defines `window.makeError()`, which returns `new
TypeError('made in wrap.js')`.

| Case | Input | Chromium | Firefox | WebKit |
|---|---|---|---|---|
| i | wrapper loaded without CORS; `fetch()` to a closed port, unhandled | **no event** (pageerror only) | event | event |
| j | wrapper loaded with `crossorigin="anonymous"` + `Access-Control-Allow-Origin` | **event** | event | event |
| k | error created by the no-CORS script, `Promise.reject(...)` from page code | **no event** | event | event |
| l | the same with the script loaded with CORS | **event** | event | event |
| m | error created by the no-CORS script, thrown synchronously from page code | `error` event (`Uncaught TypeError: made in wrap.js`) | `error` event | `error` event |

The Chromium stack in the observe runs for i and j was `TypeError: Failed to
fetch\n    at window.fetch (http://localhost:7161/wrap.js:3:43)\n    at
HTMLButtonElement.<anonymous> (…)`. This is the same shape as with the SDK
tag.

So, with no SDK involved, Chromium 156 dispatches no `unhandledrejection`
event when the rejected error was created inside a classic script loaded from
another origin without CORS. It dispatches the event when the same script is
loaded with CORS. Firefox and WebKit dispatch it in both cases. This rule, plus
the observed stacks above, accounts for C4 and C5 exactly. Nothing about how
the SDK is built is assumed.

## What this means for the corpus

The cause is not in the fixture or the harness, so nothing is re-captured. The
12 Chromium cells of C4, C5 and C6 (both environments, both versions) **stay
dropped**. They are listed in `corpus/dropped.json` with the outcome of every
attempt (the original four, plus the four re-run attempts).

For the results document, the finding is that **a customer using this SDK
loses, in Chromium, every unhandled fetch network failure and every unhandled
`res.json()` parse failure**. These are lost before grouping ever runs, so
the grouping evaluation cannot measure C4/C5/C6 in Chromium. Those incidents
are measured in Firefox and WebKit only, which leaves 4 reports per incident
per environment. The C4/C5 hard-negative pair is still in the corpus, with 4 × 4
cross-incident pairs per environment.
